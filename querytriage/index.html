QueryTriage

A decision-driven migration engine for legacy SQL — every trap found, flagged and priced

In active development — verified results, unfinished edges

Feed it a folder of .sql files — it parses the procedures, views and functions, builds the dependency graph and returns a layered DAG, a quantified risk report, and an Excel workbook where every uncertainty is a reviewable decision. What the parser cannot prove is marked inferred — never silently dropped. Same engine family as CubeTriage, different domain.

The problem

Every legacy migration starts in the same place: a database full of procedures, views and functions nobody has mapped. Circular references, dynamic SQL, deprecated syntax and dead code hide in the corpus — and nobody knows the load order. Before anyone can price the migration, somebody spends days just finding out what's actually in the database.

QueryTriage answers that question in seconds — from the .sql files alone. No database connection is needed; credentials in scripts are masked before parsing, and the whole run executes offline inside the customer's own network.

How it works

  1. Sniff — detects a .sql file, a directory of them, or a zip
  2. Sanitize — passwords, connection strings and tokens are masked in the raw text before parsing
  3. Ingest — sqlglot builds an AST per object and extracts dependency edges (confidence=parsed). Chunks that resist parsing fall back to regex and are marked confidence=inferred — the chaos stays visible, never hidden
  4. Transform — Tarjan cycle detection, topological layering, and severity-graded review flags: circular refs, dynamic SQL, SELECT *, deprecated syntax, temp-table contracts, external/missing refs, dead code
  5. Render — a markdown report, a mermaid + PNG dependency DAG, and an Excel workbook where each finding is a row with a decision column
  6. Decide — every warn flag becomes a numbered decision in decisions.json. Ignore an object or an edge and the DAG is recomputed — cycles visibly break. The review queue isn't a report about the migration, it is the migration
  7. Proposals (opt-in) — a backend interface can suggest resolutions. Code verifiers check every suggestion; the AI proposes, code verifies, a human decides

Result on a real corpus — WideWorldImporters

Microsoft's sample OLTP database project (wwi-ssdt): 336 .sql files of production-style T-SQL through the pipeline in ~22 seconds.

  • 214 objects · 448 dependency edges — procs, views, functions, tables and externals mapped
  • 4 circular dependencies — real cycles in Microsoft's own reference code
  • 26 dynamic SQL uses + 138 unresolvable references — the traps that break naive migrations
  • 68% of edges regex-inferred rather than AST-parsed — real code resists static analysis, and the report says so instead of pretending
  • 84 dropped constructs + 57 assumptions — separate provenance channels, nothing silently lost
  • 218 review findings — the workbook is the work order

Why not the existing approach?

The status quo is a senior consultant with SSMS, a text search and a spreadsheet. QueryTriage inverts that: the deterministic engine does the inventory — same input, same output — and produces an auditable artefact instead of a verbal estimate. The AI layer is deliberately boxed in: it may propose resolutions, but code verifiers check every proposal before a human sees it.

Design choices

Provenance is structural: parsed edges, inferred edges, dropped constructs and AI proposals are separate channels — a reviewer can always tell what the engine knows from what it guesses. The engine is deterministic and offline-capable: no database connection, no telemetry, designed to run inside a customer's perimeter so scripts never leave their environment.
